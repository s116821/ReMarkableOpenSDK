# Explicit development ordinary close and sampled closure

## Problem and source basis

Current native live pen/capture can show ink while the target .rm and thumbnail
remain byte-identical blank and a fresh restart/reopen shows blank. Historical PNG
is not save evidence. REM57 ordinary-reader-close-source-boundary and its actual
combined write-close-reopen experiment provide a bounded known source route.
This diagnostic does not redefine the ordinary Reader/Writer UX: closing to Library
and manual fixture reopening are not a production answer-completion requirement.
Direct native opening stays deferred. Later native settlement while preserving the
target or verified supported Previous/Next remains separate product work.

## Typed route

Add Cargo feature development-native-close (default off). Version4 canonical
Command::CloseOrdinary(ReaderFacts), requestkind7, is effectful; exact full facts
are encoded. Command::ObserveClosed, requestkind8, is read-only. Responses are
OrdinaryCloseDispatched kind9 and ClosedObserved kind10, with no body; existing
runtime/client/server nonce, sequence, operation and canonical request digest still
bind every response. Feature-disabled codecs reject these tags. Ordinary profiles
and supported-capability declarations do not change.

The distinct development-effect-close-probe-v1 profile/library selects the native
macro. It preserves all prior effect and endpoint guards. Before close: authenticate
the same retained parent/runtime, require positive caller pen-release/input/service
admission, refuse outstanding insertion/selection Busy/debt, fresh full-order native
join against requested facts, then execute the exact REM57 guarded Reader.close()
public own-metaobject QVariant slot under a once-consumed Claim. The copied REM57
close, closed_view and fixture-navigation source remains byte-identical. Failure
or timeout never repeats close. Process terminal close intent blocks later native
insertion/selection even if a caller reconnects; observing closure does not clear it.

Close-dispatched is NOT storage completion. Separate fresh closed-view observation
requires known loader composition, LoaderReady and null document; it is also NOT
a storage fence. Host receipt must keep sampled target-file changes/quiescence and
later exact target/order/image reopen proof separate. No arbitrary sleep, direct
page-open or synthesized durable receipt is introduced. Default mutation remains
disabled outside the explicit existing development effect build.

## Consumer integration

B uses the typed SDK surface with an exact local SDK snapshot override for the
next direct build. Close requires its own canonical durable attempted/unknown
journal, never an insertion/selection masquerade. Existing read-only callbacks and
full admission boundaries apply; no independent socket peer, raw wire client,
forced Busy clear or automatic effect retry. Root owns each fresh device packet,
independent recovery and actual image inspection. No local unit/lint gate is added
to the user-requested tablet iteration. These sources are not production/native
qualification or completed REM25.


## Known full diagnostic sequence: same-process fixture reopen

The actual first close trial positively dispatched close and sampled closed UI, but
showed blank pre-close pen capture and no serialized target change. The known REM57
sequence does NOT wait for changed files before reopen: it dispatches one same-
process fixture reopen immediately after sampled closure, then observes/captures
exact target; external archives establish storage afterwards. Its pen handoff is
kernel trace replay/final release, NOT a native QtTabletRelease/commit acknowledgement.
Release frame bytes are the same; initial release/pauses/path/trace differ.

Add feature-only Command::ReopenFixture(ReaderFacts), requestkind9 effectful and
Reply::FixtureReopenDispatched kind11. Use exact known reader_fixture_navigation
source, bound to the same requested full facts stored by successful ordinary close,
sampled closed view in this same backend/runtime, one consumed reopen intent and
existing Busy/debt guards. No target substitution, auto retry, generic production
open API or clearing old uncertainty. The distinct development-effect-write-reopen-v1
artifact caps reopen at1; older/default codecs/profile/artifacts remain unchanged.

Caller journals attempted/unknown reopen before wire dispatch, then takes fresh
Observe/CaptureSource matching exact target/order. A pre-reopen file sample may be
retained as evidence but must not block the known sequence waiting for file change.
Root separately compares source archives and cold reopen; no save receipt is minted
from live pixels, close, closure or the fixture-open dispatch reply. This diagnostic
is not final Reader/Writer UX and does not make direct native opening a production
completion prerequisite. SDK2.3 real retained-owner capacity remains open.
