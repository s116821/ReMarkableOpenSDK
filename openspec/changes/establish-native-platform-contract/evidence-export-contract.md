# Historical evidence export amendment (proposed)

This additive proposal follows reviewed capture implementation e0175f7483d7c3d4bea2490b15fd24a13cc34f34, integrated at 21a88a489b6561752d0dac3b7af9aec887a61f6f. Consumer amendment ReMarkableBuddiesDocs fbb2fd4cbf0352eeb71ecb32b2b3a0683a4fabd6 is consistent with the ownership and fail-closed rules here. This file is a proposed contract, not an implemented export API or qualified native protocol.

## One-way facts boundary

Add canonical lowercase UUID Display and a read-only 16-byte accessor. Add immutable historical facts exports for PageObservation, CreationReceipt and CapturedBatch. Facts are separate types with private fields and read-only accessors; they never contain a PageObservation, CreationRequest, native handle or callable capability. No constructor, deserializer, From/TryFrom conversion or import operation turns facts into an operational observation, request or guard. Original live objects remain private and unchanged.

Each export identifies an explicit experimental facts schema (initially remarkable-open-sdk/evidence-facts/1); that version is not a firmware qualification, release version or canonical request fingerprint. The consumer pins the exact SDK source revision as build provenance rather than the SDK inventing a runtime commit ID. Unknown schemas and missing required facts refuse consumer dispatch. A future native evidence schema requires separate review; synthetic facts cannot silently change meaning or origin.

Observation facts retain the original device UUID, adapter instance, session, visit, content revision, input epoch, PageKey, exact ordered page UUIDs and EvidenceOrigin. The prototype's numeric scopes are opaque process-local model tokens: they are not stable identities across process restart, globally unique scope or real device clock values. Persisting them records what the model asserted, not durable native attribution. Consumers must not fill gaps with generated IDs, Debug strings, positions or timestamps.

Receipt facts retain the operation UUID, complete source observation facts, allocation mode (and client-selected UUID if present), exact target PageKey, exact after-order, receipt revision and origin. This is historical model correlation only, not the still-unimplemented canonical request encoding/digest or durable native-assigned operation journal.

## Capture coverage and missing qualification

Capture facts retain operation UUID and source observation facts, acquisition interval, buffer generation, viewport revision, conversion procedure, capture procedure revision, optional target, native parent and all sibling derivative descriptors. Each image descriptor retains role, PNG MIME, exact byte length, SHA-256, dimensions, valid source region, pixel-edge affine coefficients and full derivation (parent digest/dimensions, crop, output dimensions, resize filter and procedure). Exact immutable media bytes remain accessible from the original batch and must be retained alongside the descriptors; a digest alone is insufficient.

The current model accepts a batch only when render generation equals buffer generation. Export both roles explicitly with their equal original value and label the binding as a synthetic equality assertion; this is not native logical frame freshness. Its interval is an injected Duration pair whose origin is local to that synthetic acquisition fixture: represent seconds as u64 and nanoseconds as u32, with clock kind SyntheticInjectedDuration and no invented globally comparable clock ID. Values from separate fixture acquisitions cannot be compared as a shared clock.

The qualification field explicitly states UnqualifiedSyntheticModel. No device/firmware adapter profile exists in this model, so the API must not synthesize one. Consumer fixtures may exercise historical persistence with synthetic origin; any path requiring native profile, native clock scope or qualified acquisition refuses these facts before effects. Adding actual native profile/clock/ownership evidence is a later reviewed contract and adapter change.

## Bounded lossless persistence

Export validates limits before copying variable data: at most 4096 UUIDs in each order, at most 4096 UTF-8 bytes in any procedure/viewport string, at most 64 KiB total variable metadata (checked accumulation of order UUID bytes and string bytes), and the existing maximum 16 images including the parent. Caller limits may be tighter; invalid limits or oversized facts return an explicit export error. Never truncate order, omit a parent/detail or replace a string. Encoded media retains its existing separately checked per-image/batch limits. These limits are not an aggregate process-memory guarantee or a native notebook-size limit: an oversized model may exist but cannot be exported under this schema.

The SDK owns the typed facts schema and exact field meanings. Consumer storage may choose its container encoding, but must round-trip all original values: UUID bytes/canonical text; u64 values without conversion through floating-point JSON numbers; Duration seconds/nanoseconds separately; and every finite geometry f64 as its exact IEEE-754 bits (u64 or fixed 16-hex-digit encoding). Enum variants have explicit schema-defined names, not Rust Debug spellings or discriminant numbers. Absence stays explicit. Unsupported/unknown/missing fields refuse the consumer operation; they are not silently dropped or defaulted. This is a historical persistence representation, not canonical request serialization for mutation or a cryptographic signing protocol.

## Verification and delivery

### Restored derivative geometry amendment

The SDK owns a production-available pure mathematical helper `capture::derive_geometry(parent_dimensions: [u32; 2], parent_affine: Affine, parent_valid_region: SourceRegion, crop: PixelRect, output_dimensions: [u32; 2]) -> Result<DerivedGeometry, CaptureFailure>`. `DerivedGeometry` exposes read-only `affine()` and `valid_source_region()` getters. This helper creates neither capture evidence nor operational authority. Trusted synthetic construction and consumer historical validation share this single SDK implementation; Buddy does not duplicate composition formulas.

Validate nonzero parent/output dimensions no greater than 32768 per axis, checked crop containment and nonzero extent, finite invertible parent affine, valid parent source region and normalized source-plane coverage. Reject empty intersection of crop and parent valid region. Derive affine and clipped/scaled valid source region using the current arithmetic and evaluation order from `Affine::derived` and `synthetic::region_for_crop`; validate resulting geometry and source-plane coverage. Preserve the existing explicit 1e-10 source-plane roundoff allowance without clamping coordinates. The dimension ceiling is a mathematical input bound, not a native device capability or media allocation promise.

For the pinned current derivation procedure, consumers compare all recomputed affine coefficients and valid-source-region fields against historical descriptors using exact IEEE-754 bits, including signed zero. Preserve the original stored bits; do not replace them with recomputed values or normalize signed zero. Exact descriptor composition equality is separate from the source-plane roundoff allowance. Unknown future derivation procedure semantics refuse interpretation until explicitly supported and pinned; the helper does not guess semantics from an arbitrary procedure string.

This is structural historical validation only: it does not decode media, prove pixels/authenticity, qualify native capture, or restore a CapturedBatch/live observation/guard. Media integrity and existing complete historical persistence checks remain required independently. Verify inconsistent but individually valid affine/region rejection, checked bounds and empty intersections, unchanged construction arithmetic, signed-zero comparison and availability without the mock feature.
