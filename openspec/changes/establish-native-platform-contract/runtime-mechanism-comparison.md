Status: October 2, 2026 architecture reconciliation and development evidence. A direct LD_PRELOAD/public-Qt startup callback has executed on the tablet and proved nonce/application-thread equality; its initial restoration receipt failed and later stock verification/cleanup are separately recorded in the [E1 evidence](e1-operator-plan.md). ## Decision and ownership

The [October 1 23:40 UTC REM-25 decision](https://linear.app/magentumdragon/issue/REM-25#comment-0cf9f583-1f09-47d1-89b1-7ff71f0a9137) supersedes the blanket production XOVI exclusion. Prefer robust direct/native mechanisms per capability. A vetted, supervised, session-scoped lazy XOVI path is eligible when those seams are insufficient. Select by measured behavior and maintenance burden, not by whether a process boundary or library name appears in an architecture diagram.

SDK owns runtime capability profiles, exact compatibility/payload provenance, activation requirements, readiness, generation invalidation, native semantic operations and recovery evidence. Buddy owns gestures, retained product intents and Supervisor orchestration; Manager owns one installation/update/disable/uninstall lifecycle for the combined Buddy artifact. These product specifications remain in ReMarkableBuddiesDocs. An injected payload may be internally packaged without becoming a separately user-managed prerequisite or alternate tablet shell.

## Activation and source continuity obligations

Cold boot starts stock xochitl with no preload activation; installing files must not activate them. An explicit consumer activation request supplies the exact approved profile/payload digest. Verify the complete dependency closure and an isolated, non-user-extensible payload directory before changing any session state. Do not use global manager environment changes or persistent xochitl overrides. The concrete runtime-only service mechanism must preserve existing vendor/user configuration and be verified on the device's actual service manager.

Model the lifecycle as Stock -> Preflight -> RecoveryArmed -> Activating -> Ready, with any failure -> RestoringStock -> DisabledForSession. Runtime process generation and fresh challenge/response bind readiness and heartbeat to the correct bridge. A heartbeat from an unrelated worker thread cannot establish GUI readiness. Healthy GUI dispatch still does not prove document-worker readiness; expose that limitation per capability.

Before activation, arm recovery outside both the injected process and the Supervisor that requests activation, for example a narrowly scoped, independently managed recovery guard with an expiring lease. This is a design candidate, not a verified systemd recipe. If the Supervisor dies before arming, no activation may begin; if it dies afterward, lease expiry must restore stock and retain the session failure latch. Test death during every state, partial configuration writes, manager restart, cleanup failure and concurrent activation requests. A tmpfs file disappearing only on reboot does not prevent a same-session restart loop. Any persistent Supervisor autostart configuration must itself be unable to select injection on boot.

After an activation restart, old handles and source guards are invalid. Retain only consumer intent plus immutable historical evidence, not a native pointer or permission to replay. Reacquire the source under the fresh runtime scope and revalidate exact page identity, visit/order/content/input requirements and action applicability. If preactivation identity or intended source is unknown, the consumer must establish a supported fresh-intent handoff or refuse continuation; an ID guessed from files or pixels cannot bridge the gap. If a native mutation could already have started, reconcile the original operation rather than resend it. Selection/tool state may also be lost; continuation requires its own evidence, not just a matching document.

## Historical experiment E0: host-owned lifecycle fault harness

Consumer coordination checkpoint: ReMarkableBuddiesDocs [`1b8ea1b7345a2983d72f6b90fa4cb982ff257c26`](https://github.com/s116821/ReMarkableBuddiesDocs/commit/1b8ea1b7345a2983d72f6b90fa4cb982ff257c26) [design](https://github.com/s116821/ReMarkableBuddiesDocs/blob/1b8ea1b7345a2983d72f6b90fa4cb982ff257c26/openspec/changes/native-buddy-page-creation/design.md) and [consumer requirements](https://github.com/s116821/ReMarkableBuddiesDocs/blob/1b8ea1b7345a2983d72f6b90fa4cb982ff257c26/openspec/changes/native-buddy-page-creation/specs/native-buddy-page-creation/spec.md) carry these host-only lifecycle boundaries and reference SDK `e2b3ebbb8c4c630e46041896bc266498518de437`. This checks the specification handoff, not implementation or device qualification. The initial Buddy harness was revised: [Docs evidence f5b4de0](https://github.com/s116821/ReMarkableBuddiesDocs/blob/f5b4de052dbdbea7bdfa29af17b61818fc85564a/openspec/changes/native-buddy-page-creation/host-lifecycle-evidence.md) records independent acceptance of `6fe9da35da79cf720511034261b60abf7e776a50` as a bounded host checkpoint with 21 tests. Guard-alone death still leaves the real fixture unprotected and blocked restoration remains failed/unqualified. SDK has read the evidence report, not repeated its suite; the E1 plan identifies required host closure. Full product/source handoff, installation and licensing gates remain open.

Coordinator accepted the host-only E0 direction after reviewing revision `17c464891334ab6b333fe68afa250707e40649d4`, with the explicit failure cases below. Main's ordinary Sol lane owns implementation and independent review; E1 is not authorized. Build an original harness around fake stock/injected child processes, an independent recovery guard and a Supervisor. Use only owned temporary configuration; no real xochitl, systemd units, device input, production payload or network.

- Preflight mismatch: zero activation state or child replacement.
- Healthy activation: one injected start, nonce-bound readiness, repeated requests without another start, explicit disable restoring the recorded stock configuration.
- Reject stale/replayed readiness and heartbeat messages from an earlier process start identity, runtime generation or activation nonce. They cannot establish Ready, refresh a lease or clear a failure latch.
- Injected constructor exits, readiness never arrives, heartbeat stops, or child repeatedly exits: at most one activation attempt per simulated boot; restore stock and latch disabled.
- Terminate Supervisor before/after recovery arming, while applying state, before readiness, after readiness and during rollback. Independently owned guard must restore stock without a message from the dead Supervisor. Simulate guard failure as a separate case: refuse activation unless recovery availability is established; after simultaneous loss, preserve the explicit limitation and prove clean simulated cold boot.
- After activation/Ready, terminate only the recovery guard or lose its readiness/lease while Supervisor remains alive. Verify stock recovery or an explicitly failed/unprotected outcome; never continue claiming healthy protected operation. Test interrupted rollback with preserved evidence and no false success on deadline expiry.
- Start two activation requests, interrupt update/uninstall, and leave partial session files. Preserve baseline configuration, reject duplicate ownership and remove only transaction-owned artifacts.

Use deterministic event-driven sequencing and an injected monotonic clock for exhaustive state tests, then bounded real child-process smoke checks: 5-second readiness deadline, 1-second heartbeat interval with a 3-second stale threshold, 5-second rollback deadline and a 30-second outer limit per case. Deadlines are watchdog bounds, never sequencing or recovery proof. These are host-test bounds, not qualified tablet timings. Record process start identities, state transitions, expected/actual stock hashes and cleanup; explicitly fail if recovery is only asserted in a log or inferred from elapsed time. Simulated boot reconstruction starts with no injection regardless of remaining persistent payload files; harmless Supervisor autostart cannot reuse stale session activation. No mock pass qualifies device behavior.

## Conditional E1: single load-only device activation and rollback

The [E1 operator/implementation plan](e1-operator-plan.md) tracks the accepted bounded E0 checkpoint, required real-process guard-loss correction, minimum stock inventory, conditional runtime-only mechanism and finite activation/restoration evidence. Exact device configuration, hashes, numeric bounds and E1 consumer counterpart remain entry gates; this is not injection authorization.

Do not execute E1 from this document. After E0 and independent review, main must produce an exact operator plan with a reviewed artifact, actual stock service/watchdog/restart configuration, dependency hashes, session-only activation mechanism, independent recovery guard and deadlines that act before the target's observed watchdog/reboot window. If those cannot be bounded safely, reject the entry mechanism before a transfer or restart.

The proposed payload is one vetted no-override extension: no native page methods, getters, document/account reads, drawing, input grabs, QML/resource replacement or arbitrary command executor. It reports its identity and a nonce-bound queued GUI ping using exact Qt headers; a separate bounded health path reports the execution context honestly. Keep all page-changing capabilities unavailable. Maintain preverified independent SSH recovery and preserve the user's source/document state; fixtures must be backed up and quiescent before a later native test.

One announced supervised activation may restart xochitl once. Verify loader/bridge identity and GUI response, then request stock rollback, prove no preload/extension mapping remains, and compare exact baseline service configuration and process health. Preserve raw operator evidence and assess visual/interaction responsiveness separately from SSH/service continuity. No automatic retry. A cold-reboot/no-injection check and controlled runtime/Supervisor fault cases require their own announced bounded stages before production selection; do not silently add them to the load-only run.

Only after lifecycle qualification should an E2 plan investigate native source reacquisition and execution-time fencing, followed by the existing insertion/preservation/persistence/interruption gates on disposable notebook and annotated-PDF fixtures. RMPP uses its own exact AArch64 provider profile, compile/ABI checks and real device tests; RM2 results do not qualify it.
