### Lifetime assessment and next bounded proof shape

Source analysis corrects the earlier suggestion that merely constructing a typed QPointer from the sampled address would make acquisition safe. [QPointer](https://github.com/qt/qtbase/blob/v6.10.3/src/corelib/kernel/qpointer.h) is a weak observer. [The shared-pointer implementation](https://github.com/qt/qtbase/blob/v6.10.3/src/corelib/tools/qsharedpointer_impl.h) copies its weak reference, but does not promote a negative strong count to shared ownership. [QObject tracking initialization](https://github.com/qt/qtbase/blob/v6.10.3/src/corelib/tools/qsharedpointer.cpp) uses -1 for this tracking case; [QObject destruction](https://github.com/qt/qtbase/blob/v6.10.3/src/corelib/kernel/qobject.cpp) clears it during the base destructor. A non-null guard therefore neither pins the object nor excludes an already-running derived destructor. A raw-address QPointer constructor must first access the object, so it cannot repair the original race.

The smallest defensible next candidate protects **registration/capture/control-block lifetime**, without dereferencing the controller: in one application-thread callback, use the exact matched QtQml private typed registry lookup for the fixed module/name/version, retain its returned QQmlType and then its SingletonInstanceInfo::ConstPtr, require the expected singleton/meta-object, and inspect `qobjectCallback.target<QQmlPrivate::SingletonInstanceFunctor>()`. If the typed target is unavailable or ABI/RTTI identity differs, refuse; never substitute reinterpretation of the historical capture address. Copy only that live functor's same-type QPointer while the retained info owns it; emit nonce, registration match, typed-target match and guard-not-cleared. No controller dereference/thread getter, functor invocation, document field or native call is part of this proof. The current nonce/thread-only payload remains unchanged.

Why this is materially different: [Qt's registry lookup](https://github.com/qt/qtdeclarative/blob/v6.10.3/src/qml/qml/qqmlmetatype.cpp) takes its recursive registry mutex and returns a referenced type; [singletonInstanceInfo](https://github.com/qt/qtdeclarative/blob/v6.10.3/src/qml/qml/qqmltype.cpp) returns an owning ref-pointer to the callback container. Retaining that container keeps its functor and weak reference alive; copying the same-type QPointer retains the weak control block, not the QObject. Exact vendor 6.10.3 headers and exports corroborate these candidate APIs. This still needs a small owned registration/unregistration/deletion fixture and exact vendor-ABI review before a new device packet. The call count is fixed, output boolean-only and at most 256 bytes; the registry mutex has no proven hard wait bound, so elapsed timeout cannot certify safe callback completion. Do not relabel this in-process reference-count/lock activity as the external R2 no-write experiment.

Avoid public qmlTypeId fallback and singleton-instance lookup for this proof: [Qt's implementation](https://github.com/qt/qtdeclarative/blob/v6.10.3/src/qml/qml/qqml.cpp) can load a module on a type-ID miss, while invoking the existing-instance functor can assign engine/ownership state. Lookup should query only the already registered fixed type, returning absent without importing, constructing an engine or invoking a factory.

Controller object access remains conditional. [Qt's threading rules](https://doc.qt.io/qt-6/threads-qobject.html) favor owner-thread access and deferred deletion, but do not prove that this native controller is application-thread confined. Required evidence is its actual construction/move/destruction discipline, including no concurrent foreign-thread delete, followed by a non-reentrant callback with no nested event processing. Calling `controller->thread()` from an otherwise unprotected pointer cannot establish that premise retroactively. The existing constructor/registration trace and R2 sample do not yet close it. A public application-window/SceneView route may simplify ownership evidence, but allWindows returns raw windows and does not itself pin them; it is no automatic lifetime solution. Neither route equates a Library/controller with the displayed document/page. Source binding and worker-time mutation guards remain separate later experiments.

## Concrete discovery chain

Static analysis of the saved executable finds construction of the document controller with a null QObject parent, followed by QML singleton registration with its known static meta-object. Later reparenting is not excluded. The registration's function wrapper allocates a capture holding a guarded pointer to the existing object, and its invoker directly forwards to Qt's SingletonInstanceFunctor. This is an existing-instance registration, not evidence that a live singleton lookup is side-effect-free.

The matching vendor QtQml library's type-by-ID path obtains a global registered-type list. Its accessor locks a recursive mutex and may initialize global state. The proposed observer must not call it. Host inspection instead identifies the already-initialized storage and confirms list pointer/count use. The vendor private headers plus an original compile-only ARM layout probe identify the type-record registration kind, base meta-object, singleton-info pointer and callback storage. These are exact-artifact research facts, not public or portable Qt ABI promises.

The candidate external read chain is:

1. Verify actual QtQml provider hash and mappings in addition to R1's executable/QtCore checks. Resolve the private registry locator relative to its verified ELF load bias, with current readable-mapping bounds. Refuse uninitialized/destroyed/unknown guard state; never initialize it.
2. Sample the fixed registered-type list descriptor and bounded pointer array. For each non-null record, read only registration kind, base meta-object pointer and singleton-extra pointer. Match the known controller meta-object exactly; do not enumerate strings, URLs, properties or source content.
3. For a matching singleton record only, inspect its singleton-info callback descriptor. Require the exact independently traced manager/invoker identities for the existing-instance functor before interpreting its capture. An arbitrary std::function or other singleton factory must remain uninterpreted.
4. Read only the capture's guarded-pointer control/object pair. Check non-null/aligned/in-range pointers, nonzero sampled strong-reference state, the controller's allowlisted vptr and QObject q_ptr backlink. Do not change reference counts or call the functor. Guarded-pointer checks and repeated reads do not acquire object lifetime ownership.
5. Reread registry/record/callback/capture/object descriptors and process identities. Any disagreement, partial read or ambiguous candidate produces incomplete/ambiguous output. Even matching samples retain non-atomicity and ABA limitations.

The exact provider hashes, ELF locators, compiler measurements and static corroboration stay in the private experiment manifest. The public helper must not embed firmware-specific addresses or accept arbitrary unrestricted memory-dump requests. Input manifests must select only this fixed semantic read shape.
