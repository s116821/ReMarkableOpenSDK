# Shutdown crash: targeted upstream evidence, October 8, 2026

Status: source-only investigation. SDK payload `71d9dbfa33ba828540fa0a9f22ec4db8aca862d6` and spent experiment `0404` remain held. No runtime change, new packet, device action or retry is authorized by this finding. The native SIGSEGV cause remains unknown.

## Concrete lead: restart during display activity

Tripletap [commit 46c6a959a6761bbda7410c905640a0ff48c2d9d9](https://github.com/rmitchellscott/xovi-tripletap/commit/46c6a959a6761bbda7410c905640a0ff48c2d9d9), September 22, adds a pre-restart idle wait specifically for xochitl 3.28+. In [issue 5](https://github.com/rmitchellscott/xovi-tripletap/issues/5#issuecomment-5779195667), the maintainer reports a xochitl use-after-free beginning with 3.28, says it was reported to reMarkable, and identifies v1.1.1 as the mitigation release. This is attributed upstream diagnosis, not a reproduced local cause or a vendor confirmation. Earlier comments discuss full-device reboot and a possible screen-paint interaction; one reporter also mentions 3.27, so the thread is not a precise compatibility matrix.

The pinned [main.sh](https://github.com/rmitchellscott/xovi-tripletap/blob/46c6a959a6761bbda7410c905640a0ff48c2d9d9/main.sh#L65-L148) sums thread user/system ticks and checks for running threads every 50 ms. It seeks 300 ms of unchanged activity, bounded by 6000 ms, before either activation or stock-toggle restart. The check applies to firmware >=3.28 or unknown firmware. It does **not** directly observe display completion. Missing PID returns success; timeout returns failure but the caller continues. It neither binds PID/start identity nor proves a native display fence. Those properties prevent adopting it unchanged as our recovery gate.

Local journal inspected for 0404: the candidate started at 15:26:33; restoration began at 15:26:34; native shutdown logged waiting for updates/display, then threads stopped and shutting down; SIGSEGV was recorded at 15:26:37. OnFailure dependencies triggered, stock replacement started, and system shutdown followed. Firmware was 3.28.0.172. The host readiness exception explains the early restoration trigger; its separately repaired error handling does not explain the SIGSEGV. There is no verified source-facts publication/read result. The new reader requires its request token; it is not an established crash participant.

**Inference:** the upstream defect is a substantially better targeted lead than an unsupported claim that the new page reader caused the crash. Firmware and early-restart timing match. Without a stack or equivalent discriminating evidence, neither matching log messages nor the upstream mitigation identifies the local faulting instruction.

## Smallest next step and retained hold

### Existing restoration semantics and feasible source increment

The frozen operator arms a separate 180-second timer for the same singleton restore service that its host `finally` starts immediately. The restore service has a 240-second start timeout. In `restore.sh`, closure is published, admission is locked, a one-shot restore claim is consumed, the owned override is removed, and systemd is reloaded. Only then does line 109 restart xochitl. Its 20-second verification deadline starts **after** that restart. Neither closure nor the claim acknowledges native display completion. The entry checks closure at guarded boundaries; it does not provide a screen-worker fence. The initial activation also restarts stock without an idle observation.

A host-only delay is insufficient: host loss still invokes the independent timer's unchanged restart. A proposed minimal consumer increment must therefore separate two cases:

1. **Before activation:** an optional bounded read-only quiet preflight can reject before installing an override or restarting stock. This is reversible and genuinely fails closed with respect to activation. Persist the exact PID/start, thread set, samples, elapsed time and outcome; invalid/missing/changing identity or deadline expiry means no activation. Its positive name must mean only CPU quiet observed, not native completion or crash-safe restart.
2. **Already armed restoration:** any quiet observation belongs to the existing singleton remote restore actor after removing the owned override and before its sole restart, so host failure cannot bypass it. A maximum six-second observation would be a proposed mitigation budget derived from upstream, not a measured safe value. It must consume an absolute recovery budget and preserve one-shot restart semantics. On expiry, neither restarting anyway nor abandoning the still-loaded process satisfies both crash avoidance and verified restoration. The former preserves exposure; the latter leaves restoration failed with payload still resident. That conflict requires an explicit recovery decision and qualifying evidence before implementation/selection.

The smallest useful source-only implementation scope is consequently a strict, owned-fixture-tested process-activity sampler and outcome decoder, without wiring it into native restoration yet. Test absent/reused PID, partial stat reads, thread-set churn, changing ticks, quiet samples and the original absolute deadline. Parse `/proc/*/stat` around its parenthesized command field rather than assuming whitespace field numbers, and check per-thread identities/ticks rather than only an aggregate that can hide churn. This sampler can measure the upstream hypothesis; it cannot resolve the display race or clear the hold. No such helper is implemented by this documentation change.

Do not patch FactsEntry destruction on this evidence: no concrete defect was identified there. Preserve the early-restoration timeline and seek an existing crash stack/core or an upstream fault signature matching the actual crash. Source-only consumer design can account for the reported restart-during-display hazard, but any proposed quiet-window check must use exact process identity, reject missing/partial samples, retain an absolute recovery deadline and record timeout as unknown. It must not silently defer mandatory recovery forever or treat CPU idleness as display ownership. Choosing what to do when no quiet window is observed remains an explicit recovery-design decision, not solved by this research.

An arbitrary sleep, the host exception repair, or switching to XOVI does not clear the native retry hold. Main alone owns any subsequent selection. Full native qualification and OpenSpec completion remain open.

Source basis: live reads of project Mem handoff v35 and prior-art v4; fresh upstream Git clones pinned above; GitHub issue/commit API output; independently inspected archived SDK startup/entry, selected restore source and saved 0404 journal. Upstream diagnosis is attributed; local causal correspondence is inference. Private evidence is retained in the operator packet, not published here.

## Actual preserved core: October 8 follow-up

Main recovered a matching-time core from the configured Memfault MAR store and verified its compressed hash before and after read-only collection. Offline inspection independently verified the uncompressed core hash and the exact saved xochitl binary. The native failure is now more specific than the journal-only hypothesis: **an invalid memory read in xochitl on a rendering call path during shutdown**. It remains neither a proven use-after-free nor a qualified recovery fix.

Direct evidence:

- ELF32 ARM notes contain faulting LWP 17423. GDB selects that thread; NT_SIGINFO independently records SIGSEGV (11), code 1 (`SEGV_MAPERR`), address `0x6d30f000`.
- PC `0x0066d004` maps through NT_FILE to `/usr/bin/xochitl`. The partial unwind proceeds through `0x0068447c`, `0x0065ec34`, `0x00667d44`, then `0x75f5dd5c`, resolved using the exact Qt Quick provider as `QQuickWindowPrivate::renderSceneGraph()`. Unwinding stops there; no complete stack or absence of an earlier payload contribution is claimed.
- Bounded private instruction inspection identifies a 16-byte read beginning at `0x6d30eff8`, crossing the faulting page boundary. The surrounding QImage scanline path and selected scalar registers indicate row 16, row pointer `0x6d30ef08`, horizontal pixels 60 through 63 and clipped width 1404. This particular read is within the observed horizontal bound; it is not evidence of a simple right-edge vector overread. Actual backing-allocation extent, ownership and deallocation history remain unavailable.
- Neither read address has an NT_FILE mapping. That excludes an identified file-backed range in the note, not anonymous mappings. The core omits captured PT_LOAD bytes for both these addresses **and the known code addresses**; omitted capture is not evidence of freed/unmapped memory. The invalid-access finding comes from SIGINFO, not from missing core bytes.

Private reproducibility evidence: `astra-core-check.py` SHA256 `7595f3678c740ef29a1624abce7bdbb0843e61b1fba3a00339255122aec1dce8`, retained beside the private core. Run with the bundled Python against the already installed Docker image; it uses network-disabled, read-only containers and a read-only evidence mount, disables GDB auto-loading/debuginfod, and emits only selected scalar registers, the partial backtrace, selected NT_FILE ranges and PRSTATUS/SIGINFO fields. Its independent standard-library ELF-note decoder asserts the thread/signal/address. It does not emit memory bytes, full register sets, manifest identities or proprietary disassembly. The row/pixel interpretation additionally relies on the separately performed bounded private instruction inspection, not on this decoder alone.

## Signature comparison and the missing completion contract

October 8 follow-up re-read all four comments of Tripletap issue 5 and the exact mitigation commit. The report matches firmware family, restart context, screen-paint suspicion and full-device reboot. It contains **no fault PC, module-relative offset, stack, allocation/free trace, exact xochitl build hash, vendor defect identifier or corrected native implementation**. Therefore the recovered rendering signature is consistent with that report, not a demonstrated duplicate. GitHub issue search returned no `renderSceneGraph` result in Tripletap; this bounded search is not proof that no private report exists. The CPU-activity mitigation does not add missing causal evidence.

The relevant upstream Qt source is [qtdeclarative v6.10.3, commit 3a714efe0672ae1ba06f09864f64957560c69b91](https://github.com/qt/qtdeclarative/blob/3a714efe0672ae1ba06f09864f64957560c69b91/src/quick/items/qquickwindow.cpp). Its file declares Qt commercial/LGPLv3/GPLv2/GPLv3 alternatives; no code is imported. This matches the provider version label, not proof that the vendor binary is an unmodified upstream build. Lines 692-697 call renderNextFrame, emit afterRendering, then endNextFrame. The documented signals have distinct scopes: afterRendering concerns recorded graphics commands; afterFrameEnd concerns frame submission; frameSwapped concerns a frame queued for presentation. sceneGraphInvalidated denotes context invalidation/resource cleanup, and releaseResources delegates to the selected window manager. None of these inspected interfaces supplies an xochitl-specific display-worker drain plus prohibition on subsequent paints. Installing a signal callback or calling releaseResources would be a runtime change, not a read-only confirmation or justified repair.
