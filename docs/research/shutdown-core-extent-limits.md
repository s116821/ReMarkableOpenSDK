## Exact missing distinction

The existing row/pixel interpretation shows a 16-byte read spanning pixels 60–63 within clipped width 1404. That excludes only the simple horizontal-right-edge explanation. Clipped width is not the backing allocation length. Establishing intended containment requires the actual image base, stride, height/row validity and allocation extent, tied to this particular source image. Computing a hypothetical base from width times four would assume the missing stride and would not establish ownership or validity.

Establishing *previously mapped* storage additionally requires an earlier mapping/allocation record for the same process and object, plus lifetime ordering. MAPERR identifies the crash-time invalid access; absent capture cannot supply the preceding map/free/unmap history. Even an ordinary mapping range is not necessarily the allocator's object boundary.

Permitted evidence that could resolve this is an already-retained exact-process image descriptor/allocation record or exact-build symbol/source information sufficient to identify such a descriptor in the saved stack, together with an existing same-process pre-fault mapping/lifetime trace. No such matching record has been identified in this bounded investigation. A read of today's stock process cannot reconstruct the old process's allocation. No new stock restart, manual action, changed capture configuration, instrumented payload or speculative fix is proposed.

## Static vtable candidate and external-buffer construction

A subsequent targeted address-reference search found one aligned direct reference to the ARM method `0x6841b0` in allocated non-executable ELF data (also checking its Thumb-tagged form). At read-only address `0x120f794`, it occupies offset92 from candidate vtable address point `0x120f738`. The preceding offset-to-top/typeinfo entries are consistent with a primary table; linked RTTI names `EPFramebufferCarta1000`, with base `EPFramebufferSwtcon`. This is a concrete static candidate, not proof of the missing live receiver vptr. Other indirect/runtime table arrangements are not excluded by this bounded reference search.

Exact table-address references lead to destructor entries and a constructor/factory path within the unwind interval `[0x66946c, 0x66b84c)`. Only directly relevant instruction ranges were examined. That path default-constructs embedded QImages at object+88 and object+104. It subsequently uses the named external-buffer QImage constructor with null cleanup function/info, copy construction and assignment into the first embedded image, then stores its address in object+100. It installs the candidate table in the same object. The actual saved pointer relationship `0x1bbb908 == 0x1bbb8b0 + 88` corroborates this layout and explains the scanner's indirection through object+100; no QImage private layout was assumed.

One directly traced buffer path allocates an array of `0xa06b00` bytes (10,513,152), replaces a pointer in separate shared state, and frees the prior array there. Its image-construction path includes 1404x1872, four-byte format and stride5616, whose product agrees with that allocation size. This is a statically available path, not recovered fault-time allocation metadata: configuration branches and the omitted buffer pointer prevent claiming that this exact allocation instance backed the failing row. The constructor also contains alternate/refusal paths. No hypothetical base computed from the crash row pointer is promoted to an observed allocation.

The table's directly connected destructor calls `QThread::quit()`, then `QThread::wait(QDeadlineTimer)`, disposes the worker, and destroys the embedded QImages at +104 and +88 before QObject teardown. The calls establish intended source ordering, not successful worker drain at the crash: the wait result is not checked on the inspected return edge, and no evidence shows this destructor executed before the failing scan. The external array's lifetime is distinct from QImage wrapper destruction; the observed constructor supplies no cleanup callback transferring that responsibility to the wrapper.

This narrows the static candidate to an embedded wrapper referring to separately managed pixel storage, with an active-image pointer selecting that wrapper. It does not prove the live class, actual allocation base/extent, a replacement/free during shutdown, or a violated lock/join contract. Those remaining distinctions require matching runtime/global-state evidence or a further concrete lifecycle edge, not a guessed race fix.
