## Startup inheritance hypothesis

The candidate journal contains a home-mount setup failure that the prior
successful worker candidate did not log. That difference is a correlation. It
does not prove a credential problem or identify an observed helper exit code.

Independent source review found a concrete process-scope defect: the pre-main
constructor requires the selected xochitl PID/start identity, but leaves
`LD_PRELOAD` in its environment. An executed helper inheriting that variable can
load the same DSO and terminate119 on the intentionally different identity.
Bounded saved-ELF analysis connects setup's backend call to a mount coroutine,
then the program `/usr/sbin/wait-for-home` through a default-constructed QProcess.
That runner starts the process and treats a normal nonzero exit code as an
error. The inspected runner does not set an explicit process environment;
[version-matched Qt documentation](https://doc.qt.io/qt-6.10/qprocess.html#environment-variables)
describes default inheritance at start. The helper/interpreter's dynamic-loader
behavior and its actual environment/exit status were not observed. The static
chain receipt is `004c2d038fe3dd4188f21fd910487c05a3a52315e45b64cd8c7beba2593490c8`.

The [narrow correction and real owned exec regression](../../openspec/changes/establish-native-platform-contract/native-insertion-child-environment.md)
must precede another fresh native packet. Clear inherited injection variables
only after profile qualification has consumed eager-binding requirements; keep
the parent's DSO resident. Explicitly supplied child environments can reintroduce
variables, so this is not a general child-process or concurrency guarantee.

Source basis: actual frozen packet, strict result bytes, scoped candidate/prior
journals, full readback/archive manifests and original startup source. Private
raw artifacts remain local under the nonce-named investigation directories.
The home-mount causal explanation is an inference awaiting a changed native run.
